# Этап №1: единая карта Башкортостана

Статус: **реализовано и проверено в GitHub и локальной тестовой среде, на VPS не развёрнуто** (12.11.2026).
Этап касается только карты. Строительство, экономика, торговля и VPS не менялись.

## 1. Единая система координат

| Параметр | Значение |
|---|---|
| Исходные координаты | WGS84, EPSG:4326 (lon, lat) |
| Игровая проекция | EPSG:32640 (UTM, зона 40N), метры |
| Клетка | 6×6 м |
| Чанк | 64×64 клетки = 384×384 м |
| Начало мира | E = 0, N = 0, одно на все населённые пункты |
| Клетка из метров | `cell_x = floor(E / 6)`, `cell_y = floor(−N / 6)` (y растёт на юг) |
| Чанк из клетки | `floor(cell / 64)`, отрицательные индексы допустимы |
| Версия контракта | `basheco-grid/1` |

Цепочка: `GPS → pyproj → метры EPSG:32640 → глобальная клетка → глобальный чанк`, обратное преобразование есть.

- Сервер (источник истины): `server/basheco/world_grid.py`, `world_projection.py` (pyproj/PROJ).
- Клиент: `client/scripts/world_grid.gd` — те же формулы (ряд Крюгера для UTM 40N). Клиент не «придумывает» координаты: его математика сверяется с контрольными точками, посчитанными сервером (`client/data/world/control_points.json`).
- Сервер отдаёт контракт в `GET /v1/world/grid`; клиент отказывается размещать участки, если версия сетки в ответе сервера не совпадает с его собственной.

Уфа (центр импортированного фрагмента) — клетка `72302, −1011032`, чанк `1129, −15798`.
Михайловка — клетка `71469, −1012286`, чанк `1116, −15817`.
Расстояние между ними в сетке 9032,3 м; геодезическое по эллипсоиду WGS84 — 9035,4 м (отношение 0,99966 = масштаб UTM в этом месте). Михайловка лежит к северо-западу от уфимского фрагмента, как и в реальности.

### Ограничения EPSG:32640 (проекция не менялась)

- Номинальная зона 40N — 54–60° в. д. Запад республики (примерно до 53,1° в. д.) выходит за неё. Проекция там математически корректна, но растут искажения.
- Масштаб (измерено pyproj): Уфа 0,999654; центральный меридиан 57° — 0,9996; 53,2° в. д. — 1,000343; 60,0° в. д. — 1,000063. То есть «6 м» клетки отличаются от 6 м на местности не более чем на ~0,04 %.
- Сближение меридианов: Уфа −0,84°, Михайловка −0,91°, западный край до −3,1°, восточный до +2,4°. «Север сетки» не совпадает с истинным севером на эту величину.
- Расширение мира за пределы республики потребует осознанной миграции CRS, а не тихой смены масштаба.

## 2. Геоданные

Источник — OpenStreetMap (ODbL 1.0, © OpenStreetMap contributors). Ничего не придумывается и не выравнивается по клеткам.

Найдено при аудите: у Уфы в репозитории лежали исходные lon/lat, у Михайловки — только производные локальные метры. Исходные выгрузки заново получены с OSM API по тем же bbox, что записаны в старых манифестах. Сверка: все 7921 вершины старых данных совпали с узлами OSM (расхождение 0 м), все старые идентификаторы найдены.

Конвейер:

1. `tools/import_osm.py BBOX file.osm` — ручная загрузка (сырые XML не коммитятся: в них имена участников OSM).
2. `python -m basheco.import_osm_xml …` → `server/geodata/sources/<id>.json`: WGS84, идентификаторы `way/…`, `relation/…`, тип и подтип объекта, название; без метаданных участников.
3. `python -m basheco.world_atlas` → `client/data/world/` в EPSG:32640.

Формат атласа (`basheco.world_atlas/2`): `manifest.json` (CRS, версия сетки, источники с URL и временем загрузки, населённые пункты, индекс чанков), `chunks/chunk_{x}_{y}.json` (`basheco.world_chunk/2`), `large.json`, `boundaries.json`, `elevation.json`, `control_points.json`. Точки — `[E, N]` в метрах с округлением до 1 см.

Правила геометрии:

- Дороги и водотоки сохраняют все исходные вершины и режутся ровно по границам чанков; обе половины получают одну и ту же точку разреза, поэтому швов нет.
- Здания и площадные объекты хранятся один раз — в чанке центра своего охвата. Клиент держит кольцо в один чанк вокруг экрана.
- Площадные объекты крупнее этого кольца лежат в `large.json` (сейчас 2 объекта).
- У каждого фрагмента уникальный `uid`; дублей нет (проверяется тестом).
- Сборка детерминирована: пересборка обязана дать побайтно те же файлы (тест).

Текущее содержимое: 944 объекта OSM (776 зданий, 159 дорог, 6 лесных участков, 3 водных), 1094 фрагмента, 56 чанков, 359 КБ.

**Покрытие частичное.** Уфа — фрагмент центра ~130×200 м (bbox 55.971,54.7377–55.973,54.7395), Михайловка — ~1,5×1,9 км. Остальная территория республики пуста, потому что не импортирована; на карте рамкой показана граница загруженных данных. Мультиполигоны импортируются только внешними контурами (без «дыр»); 1 отношение в уфимском фрагменте не собрано и пропущено.

## 3. Клиент Godot

- Одна сцена, один атлас, одна сетка. Отдельных карт городов и их начал координат нет; старый несовмещённый OSM-оверлей удалён.
- Выбор населённого пункта в меню **переносит камеру** на его реальные координаты.
- Точность: глобальные клетки — целые числа. Всё рисуется относительно `render_origin` — глобальной клетки, выровненной по чанку и следующей за камерой. Canvas с 32-битными числами не видит «миллионных» координат.
- Чанки — узлы `geo_chunk_node.gd`: геометрия рисуется один раз в координатах клеток, при панорамировании меняется только трансформация узла.
- Потоковая загрузка: чанки на экране плюс кольцо в 1 чанк, не более 64 одновременно, не более 2 файлов за кадр; далёкие освобождаются.
- LOD по масштабу: ≥0,85 — полная детализация (спрайты, сетка клеток); ≥0,3 — без спрайтов и сетки; ≥0,12 — только основные дороги и площадные объекты; ниже — обзор республики (границы и подписи населённых пунктов, детальные чанки не держатся).
- Масштаб 0,004–2,4; сенсорное управление (перетаскивание, щипок) сохранено.
- Отладочная строка показывает клетку и lon/lat под центром камеры — для проверки на устройстве.
- Ширина дорог берётся по классу OSM (стиль отрисовки, не геодезические данные).

## 4. Совместимость со старыми данными

Старые участки адресовались `(sector_id, tile_x, tile_y)` в собственной сетке 0…4096 каждого посёлка. Эти числа **не являются** мировыми клетками и никогда так не трактуются.

Миграция `015_world_grid_link.sql` только добавляет:

- таблицу `world_legacy_sector_anchors` — как старый клиент привязывал сектор к местности (константы из `geo_background.gd` и манифестов v1 на коммите `69b1991`);
- столбцы `world_cell_x`, `world_cell_y`, `world_cell_source`, `world_cell_offset_m` в `world_plots` (NULL = не размещён);
- ограничение-исключение: одна физическая клетка принадлежит не более чем одному участку во всём мире.

`python -m basheco.world_compat` (вызывается и из `basheco.migrate`) размещает участки: угол старого тайла → локальные метры → WGS84 (точное обращение старой проекции) → EPSG:32640 → ближайший угол мировой клетки. Участок сдвигается целиком не более чем на 4,25 м (половина диагонали клетки); сдвиг записывается. Сектора Уфы и Михайловки географически перекрываются, поэтому проверка пересечений теперь общая для всех посёлков.

Гарантии: `id`, `sector_id`, `tile_x/y`, владельцы, здания и история не меняются; ничего не удаляется. Если два участка претендуют на одну клетку или у сектора нет привязки, участок остаётся неразмещённым, попадает в отчёт и **не рисуется** — положение не выдумывается. Команда идемпотентна.

API:

- Без изменений: `POST /v1/world/plots`, `GET /v1/world/sectors/{id}`, `GET /v1/world/sectors/{id}/viewport`, `POST /v1/world/buildings`. В ответах добавились поля `sector_id`, `world_cell_x`, `world_cell_y`.
- Новое: `GET /v1/world/viewport?min_cell_x&min_cell_y&max_cell_x&max_cell_y` (глобальные клетки, все посёлки, нужна сессия), `GET /v1/world/grid`.

## 6. Порядок развёртывания (не выполнялся, требует отдельного разрешения)

1. Резервная копия базы.
2. Обновить сервер: образ с `pyproj`, затем `python -m basheco.migrate` — применит 015 и разместит существующие участки. Проверить строку `World grid backfill …`: `still_unmapped` должно быть 0, иначе разобрать список вручную.
3. Только после этого распространять новый APK: старому серверу неизвестен `/v1/world/viewport`, новый клиент покажет карту, но не участки.
4. Проверить на 3–5 реальных устройствах: перемещение, масштаб, переход Уфа↔Михайловка, FPS и память.

## 7. Известные ограничения

- Покрытие геоданных — два фрагмента; полная Уфа и остальные населённые пункты не импортированы. Архитектура этого не требует менять: новый источник добавляется шагами из раздела 2.
- Для Уфы целиком OSM API не подойдёт (лимит узлов): нужен региональный экстракт (PBF) и нарезка крупных полигонов по чанкам — сейчас такие полигоны идут в `large.json`, что годится лишь для малого их числа.
- Чтение чанков идёт в основном потоке (маленькие файлы, ≤2 за кадр); фоновая загрузка — возможная оптимизация после замеров на телефоне.
- Участок при размещении сдвигается до 4,25 м и остаётся выровненным по мировой сетке, а не по истинному северу (разница ~0,84°).
- `POST /v1/world/plots` по-прежнему принимает старые координаты сектора; создание участков по мировым клеткам относится к механике покупки земли и в этап №1 не входит.
- `server/tests/http_smoke.py` (ручной сценарий) ссылается на удалённый квартал `ufa-prototype-01` и не работал ещё до этапа; не менялся.
